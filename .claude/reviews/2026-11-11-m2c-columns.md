### Concurrency analysis (what I verified)
- **Deadlocks:** I found none. No transaction upgrades its lock. Escalation rolls the attempt back and starts a new transaction with `FOR NO KEY UPDATE`. Shared-lock transactions write a single row each, so the only wait between them is on the unique index entry of the other transaction, and that wait cannot form a cycle. `rename` takes no board lock and updates a single row, so it cannot close a cycle either. Board delete/rename conflict with FOR SHARE in the expected way, and after a board delete `lockBoard` returns 0 rows → 404.
- **Lost updates / stale reads:** `lockBoard` is the first statement and `listForBoard` comes after it. Under READ COMMITTED the list therefore sees everything committed by the holder of the conflicting lock. `rankBetween` is deterministic, so two writers using the same snapshot of the same gap always collide on the unique constraint instead of silently interleaving. This is a sound design.
- **Rebalance:** this path runs only under the exclusive lock, so `setRanks` (a single raw `UPDATE ... FROM unnest`) cannot collide with concurrent writers. The deferred-to-end-of-statement check makes rewriting all ranks in one statement correct. The raw SQL is fully parameterised (tagged template, `::text[]` casts) and scoped by `boardId`, so there is no injection risk.
- **Relaxed (lenient) retry:** it places the column directly after `afterId`, which is still between `afterId` and `beforeId`. A reversed pair still returns 409. I found no case where it puts the column on the wrong side of either neighbour (see MINOR 1 for a contract note).
- **pg_stat_activity tests:** API tests run with `fileParallelism: false`, so other test files cannot inflate the lock-waiter count. The waits really are lock waits (row lock on X/Y, board-row lock). The 3 s wait timeout fits inside Prisma's default 5 s transaction timeout. I consider them reliable; see MINOR 4 for a small robustness note.

### MINOR
1. `packages/shared/src/schemas/column.ts` (doc of `positionShape` / `moveColumnSchema`). The doc promises that non-adjacent neighbours always fail with `INVALID_POSITION`. After a rank collision, however, the server accepts any `afterId` that precedes `beforeId` and places the column directly after `afterId` (`column.service.ts:108`). This also covers columns that drifted apart for reasons other than the colliding insert. The behaviour is reasonable, but the client-facing contract should state it. → Add one sentence to the shared doc comment: "if a concurrent change fills the same gap, the column is placed directly after `afterId`".
2. `apps/api/src/repositories/column.repository.ts:177-187`. Interactive transactions use Prisma's defaults (`maxWait` 2 s, `timeout` 5 s). When many requests queue on one board's exclusive lock, each one holds a pool connection while it waits. A slow queue therefore ends in `P2028`, and the error handler turns that into a generic 500. This is not a problem at thesis scale. → Consider passing explicit `{ maxWait, timeout }` and mapping `P2028` to 409 `RANK_CONFLICT`/503, or setting a `lock_timeout`.
3. `apps/api/src/repositories/column.repository.ts:182`. Every `P2002` inside a column transaction is turned into `RankCollisionError`. The comment explains this is safe today (cuid ids), but if a unique constraint is added later (for example on title) it would silently be retried and then reported as `RANK_CONFLICT`. → Optionally check that `err.meta.target` / the constraint name is `Column_boardId_rank_key` and rethrow anything else.
4. `apps/api/src/routes/column.routes.test.ts:172-181, 656-666`. If `waitForLockWaiters` times out, the transaction rolls back but the `pending` request promise is never awaited, so a slow CI run would also produce an unhandled rejection. The first concurrency test also does not assert that a collision actually happened (the deterministic retry test covers that, so this is acceptable). → Optionally attach `pending?.catch(() => undefined)` before rethrowing.

### What I verified
- **`set_config` scope and ordering:** `set_config('lock_timeout', $1, true)` uses `is_local = true`, so it behaves like `SET LOCAL` and is reset at COMMIT/ROLLBACK. It cannot leak to the next user of the pooled connection. The call is awaited on `tx` before `fn` runs, and the first statement of `fn` is `lockBoard`, so the timeout already applies to the board-row lock. It also applies to the unique-index waits between shared-lock writers. The value is passed as a bound parameter (`'2000ms'`), which is valid input for `lock_timeout`. The integration test confirms this: with a lock held via `FOR UPDATE` and `lockTimeoutMs: 100`, the call fails with `BoardBusyError` in under 1.5 s.
- **503 path:** `ServiceUnavailableError extends AppError(503, code)`, so the existing `AppError` branch of `errorHandler` returns `{ error: { code: 'BOARD_BUSY', message } }`. `BOARD_BUSY` was added to `COLUMN_ERROR_CODES` in shared. The service maps the error once in `inLockedBoard`, and `withRankRetry` rethrows anything other than collision/rebalance, so a busy board is never retried. The unit test confirms there is exactly one transaction call, and the integration test confirms 503 with no row written.
- **P2028 breadth:** the mapping is confined to `ColumnRepository.transaction`. Prisma uses P2028 only for interactive-transaction API errors: not started within `maxWait`, expired or closed, or used after close. The first two are exactly the "busy" case. The third would be a programming error, and it gets reported as 503 too (see MINOR 1). P2028 does not cover ordinary query or constraint errors, so this is acceptable.
- **Timing tests:** the margins are generous (100 ms lock timeout vs a 1500 ms assertion; 50 ms tx timeout vs a 200 ms sleep, and P2028 happens on either the set_config or the commit side). API tests run with `fileParallelism: false`. I see no flakiness risk beyond MINOR 2.
- **Privacy:** none of the new or changed files mention tooling, `docs/` or ADR numbers.

### MINOR
1. `apps/api/src/services/column.service.ts:193-197` with `apps/api/src/middleware/error-handler.ts`. `BoardBusyError` keeps the original error as `cause`, but `ServiceUnavailableError` drops it, and `errorHandler` does not log `AppError`s. If a P2028 ever comes from a bug (for example a query on `tx` after `fn` resolved, or an unawaited promise), it surfaces as a silent 503 with no trace. → Pass `{ cause: err }` through to `ServiceUnavailableError`/`AppError`, and/or `req.log.warn({ err })` for `AppError`s with status >= 500 (or at least in the `BoardBusyError` branch).
2. `apps/api/src/routes/column.routes.test.ts:156,178,670`. `waitForLockWaiters` waits up to 3000 ms, but the requests under test now use the default 2000 ms `lock_timeout`. On a very slow run, the first waiter could time out (503) before the second appears, and the failure would then look like "expected 200, got 503" instead of the helper's clear message. This is very unlikely in practice. → Keep the helper timeout below `DEFAULT_COLUMN_TRANSACTION_OPTIONS.lockTimeoutMs` (for example 1500 ms), or build the test app's repository with a larger `lockTimeoutMs`.
